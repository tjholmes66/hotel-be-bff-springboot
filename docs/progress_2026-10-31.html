Security Considerations

Overview of Security

This BFF is using Oauth2 Client as followed the BFF (back-end for front-end) security pattern. As you know, this follows that this BFFis tightly tied to the Authentication tool, and in this case it's KeyCloak. I saw KeyCloak in multiple job descriptions, and I wanted to know more about this tool. In building multiple apps over the years, it is important to have security in mind from the start, and I did NOT want any responsibility for saving/storing/encrypting username and passwords in my own app or database. For that reason, we use keycloak. However, for development purposes, at this time, Keycloak is using it's built in memory H2 database rather than the preferred PostgreSQL database.

Keycloak Configuration

As you may, or may not, know KeyCloak is a new tool for me. I have used LDAP, Auth0, Okta, Social Media Logins, and Forgerock OpenAM for authentication tools. Within KeyCloak, we created a realm, then we created the client. The "client" had to be configured for this application in regards to the web origin, the callback url, and the logout urls. Also, we wanted to create particular roles/groups for this which had to be configured to add to our token. A new field, Phone Number is also added and is required. These were all minor changes in Keycloak for this application.

Security Workflow

This is nothing new, and is a process I knew for some time, and that is the Oauth2 client pattern. So, from the UI page, it points back to the BFF app which then calls Keycloak. The username/password credentials into Keycloak which takes away that responsibility from our application. We do not store usersnames/passwords encrypted, hashed, or otherwise into our database. We do have a User table, but we do not store passwords. That is the purview of Keycloak, or any other authentication tool we might use in the future. Once a user is authenticated, then Keycloak sends a code to the BFF where an exchange takes place for token and the User is stored in the session within the BFF. That's right, the BFF is NOT stateless at this time, and won't be, BUT the Microservices will be! Also, at this time a JSESSIONID cookie is created on the UI, so the UI no longer has to worry about tokens. This is as secure as secure can get, and follows a very normal pattern.

Other Security Considerations

We also made sure our SpringBoot Security Config is set correctly to make sure all API's are secured. Login and Logout are properly setup to the correct url. CORS and CSRF issues are also taken into consideration.

Two UI's for the Price of One

Once I got the framework started, and commited into a GitHub Repository, then I was able to start making changes. I got started with splitting the App into two distinct UI's, but within this same MonoRepo. There is a GUEST Portal and a STAFF Portal. A user with KeyCloak has to authenticate. A User is assign Groups, and there is one Group for GUEST and several for Hotel Staff. Once a User is authenticated against KeyCloak, the UI is able to make a call to the /api/v1/me REST API (Controller), get the users information and with a list of groups/roles/authorities, then we are able to use typescript to build the menus we want for the UI.

Front-end Layout

The layout that we have for both the Guest and Staff Portal is the same, and it is a traditional view. We have a Header, we have a Footer, we have a Left-Side Menu that is controlled by the User Groups, and we have a main content area.
